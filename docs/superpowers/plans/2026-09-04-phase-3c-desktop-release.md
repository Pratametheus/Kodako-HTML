# Fase 3c — Desktop & Rilis: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A teacher can find a Windows installer on GitHub Releases (built automatically when the maintainer tags a release), install "Game HTML" with a real icon, and — inside the app or on GitHub — read a short Bahasa Indonesia guide covering how to start, the two modes, saving/exporting, and basic troubleshooting.

**Architecture:** No app behaviour changes. Four independent additions: (1) a deterministic app-icon source PNG generated by a committed Node script + the Tauri CLI's `icon` subcommand populating `src-tauri/icons/` (image processing only — needs no Rust toolchain, unlike `tauri build`), with `tauri.conf.json` corrected to reference the real output files; (2) a GitHub Actions **release** workflow that builds the Windows installer on a `windows-latest` runner (which has Rust preinstalled) when a `v*` tag is pushed, and attaches it to a GitHub Release; (3) an in-app **Bantuan** (Help) overlay reachable from the editor header; (4) a real `README.md` quickstart. This machine still has no Rust/MSVC — `tauri build` itself is verified only by the new CI job when a tag is pushed (or by the maintainer locally later), exactly as Fase 0 left it.

**Tech Stack:** Node built-in `zlib` (PNG encoding — no new deps), `@tauri-apps/cli` (already a devDependency, its `icon` subcommand needs no Rust), GitHub Actions (`tauri-apps/tauri-action`), vanilla TS, Vitest/jsdom, Playwright.

**Spec:** `docs/Design.md` §14 (build & rilis — web + Tauri + CI); `docs/ROADMAP.md` → "Fase 3 — Poles & paket desktop" (Tauri installer, CI job, panduan); `docs/PRD.md` §3/§4 (guru sebagai pengguna, skenario pemakaian).

## Task 1: Deterministic app-icon source + populate `src-tauri/icons/`

**Files:**
- Create: `scripts/gen-app-icon.mjs`
- Modify: `src-tauri/tauri.conf.json` (icon list, if the real `tauri icon` output differs from the current placeholder list)
- Test: `tests/unit/app-icon.test.ts`

**Interfaces:**
- `scripts/gen-app-icon.mjs` — a Node ESM script, `export function renderIconPng(): Buffer` (a pure function so the test can call it directly) + a thin CLI (`if (import.meta.url === \`file://${process.argv[1]}\`) { … write to argv[2] or a default path … }`).
- `renderIconPng()` builds a **1024×1024, 8-bit truecolor (colour type 2), no-alpha PNG** matching the existing `public/favicon.svg` design scaled up: background `#4C97FF` (76,151,255) filling the whole square; a white bar at the favicon's proportions scaled ×32 (favicon `rect(x=7,y=9,w=18,h=5)` on a 32×32 canvas → at 1024×1024 that is `x=224,y=288,w=576,h=160`); a yellow `#FFD500` (255,213,0) bar at the favicon's second rect scaled ×32 (`rect(x=7,y=18,w=12,h=5)` → `x=224,y=576,w=384,h=160`). No rounded corners (OS icon templates handle corner masking); no anti-aliasing needed (hard-edged rectangles are fine at this resolution).
  - PNG encoding, byte-for-byte:
    1. Signature: `Buffer.from([137,80,78,71,13,10,26,10])`.
    2. **IHDR** chunk data (13 bytes): width `1024` (UInt32BE), height `1024` (UInt32BE), bit depth `8`, colour type `2`, compression `0`, filter `0`, interlace `0`.
    3. **Raw scanlines**: for each of 1024 rows, one filter-type byte `0x00` followed by 1024×3 RGB bytes computed from the rectangle test above (background colour unless the pixel falls inside the white or yellow rect, in that priority — yellow bar is drawn after/does not overlap the white bar per the coordinates above, so order doesn't matter here, but check the white rect first, then yellow, then background for clarity).
    4. **IDAT** chunk data: `zlib.deflateSync(rawScanlineBuffer)` — Node's `zlib.deflateSync` already produces a complete zlib stream (2-byte header + deflate data + 4-byte Adler-32), which is exactly the byte sequence a PNG `IDAT` chunk expects. No manual Adler-32/CRC of the *compressed* data is needed.
    5. **IEND** chunk: empty data.
    6. Each chunk is serialised as: 4-byte length (BE) of the data + 4-byte ASCII chunk type + data + 4-byte CRC32 (BE) computed over `type + data` using the standard PNG/zlib CRC-32 (polynomial `0xEDB88320`, standard reflected table-driven algorithm — implement the classic 256-entry table generator: for `n` in 0..255, `c = n`; repeat 8 times `c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1)`; `table[n] = c`; then CRC of a buffer starts at `0xFFFFFFFF`, XOR-folds each byte through the table, and the final CRC is `(running ^ 0xFFFFFFFF) >>> 0`).
  - CLI: writes the PNG to `process.argv[2] ?? 'src-tauri/icon-source.png'`.
